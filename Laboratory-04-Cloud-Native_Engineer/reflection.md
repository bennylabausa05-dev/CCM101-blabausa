## Mission Reflection

Doing this lab really showed me how different containers are from virtual machines, especially when it comes to speed. Setting up a VM means installing a full operating system, which can take several minutes just to boot up before you even get to install the app you actually need. With Docker, I pulled the Nginx image and had it running in seconds. There was no OS to install because the container just uses the host's kernel and only brings the app itself, so the whole process felt almost instant compared to a VM.
Port mapping was something I didn't fully get at first, but it makes sense now. A container is isolated from the host by default, so anything running inside it, like Nginx on port 80, can't be reached from outside unless you open a path. Using `-p 8080:80` connects port 8080 on my machine to port 80 inside the container, so my `curl` command could actually reach the web server. Without that mapping, the container would still be running, but I'd have no way to access it.
When I ran `docker rm`, I learned that it deletes the container itself, meaning its writable layer, its settings, and any data that wasn't saved outside the container. But the image, like `nginx`, stays untouched, so I can run a brand new container from it again anytime. This showed me that containers are meant to be temporary, while images are the reusable part.
Thinking about DevOps, containers make it easier for developers and operations teams to work together because the environment moves with the app. Developers don't have to worry about "it works on my machine" issues since the container carries everything it needs, and operations teams can deploy the same image anywhere without reconfiguring servers manually.
As for my GitHub portfolio, this lab added another real, hands-on project that shows I can work with Docker, document my process clearly, and explain technical concepts in a simple way, which is useful for future employers to see.
